# Paper 19 — Toolformer: Language Models Can Teach Themselves to Use Tools

## Paper contribution

Schick et al. introduce **Toolformer**, a self-supervised procedure for teaching a pretrained language model **when to call an external tool, which tool to call, and what arguments to supply**. The key novelty is that the model generates candidate API annotations itself and keeps only calls that measurably improve its ability to predict subsequent text.

## Self-supervised data-generation method

Starting from ordinary text, Toolformer:

1. uses a few manually written API demonstrations to sample candidate calls at plausible positions;
2. executes each candidate call;
3. compares future-token loss with and without the returned tool result;
4. retains a call only when including the result lowers loss by at least a threshold `τ_f`;
5. inserts retained calls into the original corpus and fine-tunes the LM with a standard language-modeling objective.

This is important because the supervision signal is **utility to the model**, not a manually labeled per-task tool-use dataset.

## Model and tools

- Base model: **GPT-J, 6.7B parameters**.
- Five tools are studied:
  - Atlas-based question answering;
  - a calculator supporting `+`, `-`, `*`, `/`;
  - BM25 Wikipedia search over the KILT dump;
  - NLLB-600M machine translation into English, covering 200 languages;
  - a calendar API returning the current date.
- At filtering threshold `τ_f=1.0`, retained examples include **18,526 QA calls, 60,974 Wikipedia-search calls, 994 calculator calls, 20,587 calendar calls, and 1,034 translation calls**.

## Downstream evaluation

Toolformer is evaluated zero-shot: the user specifies the task, but does not give task-specific tool-use examples. Baselines include original GPT-J, GPT-J fine-tuned on the same CCNet text without APIs, Toolformer with APIs disabled, OPT-66B, and GPT-3 175B.

Representative LAMA results:

- SQuAD subset: GPT-J 17.8, Toolformer-disabled 22.1, **Toolformer 33.8**, GPT-3 26.8.
- Google-RE: 4.9 → 6.3 disabled → **11.5 Toolformer**, GPT-3 7.0.
- T-REx: 31.9 → 34.9 disabled → **53.5 Toolformer**, GPT-3 39.8.

Thus the gain is not merely from extra fine-tuning: disabling tool calls loses a large fraction of the improvement.

## Language-modeling and scale evidence

- With tools disabled, Toolformer has essentially the same perplexity as GPT-J+CC on the studied corpora: **10.3 WikiText / 10.5 CCNet**, indicating that adding tool-use examples did not materially degrade ordinary language modeling in this setup.
- Across GPT-2 sizes, useful tool use emerges around **775M parameters**; smaller 124M/355M models obtain little benefit, while larger models increasingly exploit APIs.

## Decoding analysis

The paper modifies greedy decoding so the model can initiate an API call when the API token is among the top-k tokens (`k=10` in main experiments). On T-REx, increasing k changes API-call frequency from 40.3% at k=1 to **98.1% at k=10**, with overall score rising from 47.8 to **53.5**. On WebQuestions, k=10 yields 100% API-call frequency and 26.3 score. The analysis also observes that the model is somewhat calibrated at k=1—examples on which it chooses not to call a tool are easier—but this calibration disappears as k grows.

## Limitations

The authors identify several limits directly relevant to agents:

- **No chained tool use:** outputs of one tool cannot be fed into another because each tool's training calls were generated independently.
- **No interactive browsing:** a search call returns one textual result format; Toolformer does not iteratively inspect many results or refine queries.
- **Prompt sensitivity:** whether an API is called can change with input wording.
- **Sample inefficiency:** more than a million source documents may yield only a few thousand useful calculator examples.
- **No tool-cost awareness:** call decisions ignore computational or monetary cost.
- Filtering is imperfect: some unhelpful calls still reduce perplexity and survive.

## Relevance to generalized web automation and extraction

Toolformer is P0 evidence for **learned tool invocation**. It shows that the interface between an LLM and external functions can itself be learned from weak/self-supervision. However, generalized web agents need capabilities that Toolformer explicitly lacks: chained tools, iterative search/browsing, stateful actions, error recovery, permissions, cost-aware planning, and evidence/provenance validation.

## Synthesis statement

Toolformer shows that a 6.7B LM can bootstrap useful API-call behavior from its own predictions and outperform much larger no-tool baselines on knowledge tasks, but its inability to chain tools or browse interactively, plus prompt sensitivity and missing cost awareness, mark a clear boundary between learned function calling and a generalized web agent.
