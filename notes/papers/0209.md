## Analysis

<!-- note-body-start -->
### Research problem and contribution

MAGIS addresses repository-level GitHub issue resolution by assigning software-evolution responsibilities to four agents: Manager, Repository Custodian, Developer, and Quality Assurance Engineer. The paper first diagnoses direct-LLM failures, then uses the resulting factors to design the multi-agent workflow.

### Method and evaluation

The Manager decomposes and coordinates work, the Custodian retrieves repository context, the Developer edits code, and QA reviews/tests the change. Evaluation uses SWE-bench and compares MAGIS with direct GPT-3.5, GPT-4, and Claude-2 use. MAGIS resolves 13.94% of issues in the primary reported setting—about eight times the direct GPT-4 rate used by the authors. Component analysis attributes additional resolved issues to repository retrieval and QA, although absolute performance remains modest.

### Limitations and critical assessment

SWE-bench outcomes depend on repository setup, test execution, context retrieval, and model version. More roles also mean more calls, so the experiment does not fully separate organizational design from extra compute. A 13.94% resolution rate is a meaningful improvement but also evidence that most realistic issues remain unsolved.

### Relevance to the survey

MAGIS is a concrete example of role-specialized tool use with executable verification. Web-agent systems can adopt the same separation between planning, state retrieval, action, and QA, while reporting end-to-end success rather than plausible patches.
